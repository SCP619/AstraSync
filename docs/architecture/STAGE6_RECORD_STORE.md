Status: merged (PR #13 and the Stage 6 completion PR), 2026-11-07. Off in the API and worker unless `ASTRASYNC_RECORD_STORE_PATH` is set; on by default in the dev stack.
All data is labelled synthetic (`ASTRASYNC-SYNTHETIC-SCALE-DATA v1`), generated by
`astrasync_data.synthetic_scale`. No real or restricted data was used. Raw results are in
`traficom-integration/backend/benchmarks/results/`.

Machine: AMD Ryzen 7 4800H (16 logical CPUs), 15.4 GiB RAM, Windows 11, local NVMe disk,
PostgreSQL 16 (pgserver) on the same machine, Python 3.11.

## 2. Why 50 MB became 1.88 GB in PostgreSQL

Measured with `benchmarks/storage_breakdown.py` on 50,000 rows (5.5 MB source) through the real
ingest code, after `VACUUM ANALYZE`. The ratio matches the earlier 50 MB run (39.5× vs 38×).

| Where | Bytes | Share |
| --- | ---: | ---: |
| Record tables total | 217.9 MB | 100 % |
| Heap (row data) | 174.4 MB | 80.0 % |
| Indexes (13) | 43.3 MB | 19.9 % |
| TOAST | 32 KB | ≈ 0 % |
| Integrity verification (`artifact_integrity_checks`, 4 rows) | 80 KB | ≈ 0 % |

Per stored record (2.4 quality findings each):

| Table | Bytes per record | Largest parts |
| --- | ---: | --- |
| `source_record_locations` | 2,223 | `field_aliases` 647 B, `raw_fields` 609 B, `analysis_eligibility` 128 B, `raw_record_sha256` 65 B |
| `reference_station_records` | 843 | normalized `fields` JSON 615 B |
| `record_quality_findings` | 843 (350 per finding) | text `finding_id` and `source_record_id` keys (~40 B each), plus their indexes |
| `source_library_search_index` | 450 | repeated `publisher`, `filename_original`, `artifact_id`, `source_id`, `tenant_id` |

Causes, in order of size:

1. **Repeated per-artifact metadata, stored per row: about 915 B of every 2,223 B location row.**
   `field_aliases` has 1 distinct value across 50,000 rows, `parser_version` and `schema_version`
   1, `analysis_eligibility` 7. The search index repeats 5 columns that have one value per artifact.
2. **JSON stored uncompressed.** The columns are `json`; each value is under PostgreSQL's 2 KB TOAST
   threshold, so none is compressed, and every row repeats every key name.
3. **The same values held several times.** Raw values (`raw_fields`), normalized station fields and
   search columns are stored separately for each record.
4. **Indexes: 20 %.** Long text primary keys (`<artifact>-<ordinal>`, `<record>-<n>`) are indexed
   in four tables, plus foreign-key and search indexes.
5. **Page overhead.** 28 B tuple header and line pointer per row, and ~18 % unused space in the
   location heap (rows of ~1.7 KB fit 4 to an 8 KB page).

Corruption verification does **not** contribute meaningfully: the integrity-check rows are 80 KB
in total, and the only per-row verification value, `raw_record_sha256`, is 65 B (1.5 %). Write-ahead
log (805 MB server-wide during the runs) is transient and not counted.

## 3. New architecture (proposed, behind a setting)

```
PostgreSQL (transactional)                      Record store directory (immutable)
  tenants, users, roles, entitlements             datasets/<tenant>/<artifact>/<attempt>/
  sources, artifacts, integrity checks              records.parquet   one row per record
  jobs, audit, cases, reviews, drafts               findings.parquet  one row per finding
  record_datasets  ── manifest ─────────────────►  staging/<artifact>/<attempt>/   (never read)
```

- **On** when `ASTRASYNC_RECORD_STORE_PATH` is set for the API and worker. **Unset** keeps the
  PostgreSQL index exactly as before. Default: unset (reversible).
- **Format** `records-parquet/1`, zstd, dictionary encoding. Raw values are JSON text in the
  adapter's key order, so they read back unchanged. Per-artifact constants (publisher, filename,
  classification, synthetic flag, parser version) live once, in the manifest.
- **Reads** return the same ORM row classes as the PostgreSQL index, as transient objects, so
  response building is shared. Tested: every search variant, record detail, source location and
  preview page give byte-identical API responses from both stores on the same 260 records
  (`test_record_store.py::test_api_responses_match_the_postgresql_index`, SQLite and PostgreSQL).
- **Unchanged:** all REST routes and OpenAPI (`contract.export --check` passes, no UI drift),
  `SourceAdapter`, `RFMethod`, `CriterionResolver`, permission rules, audit, provenance (artifact
  SHA-256, record location, `raw_record_sha256`, parser and schema versions).
- **Internal additions** for joint review (DECISIONS A38): `PipelineContext.records`,
  `LibraryRuntime.records`, optional `records` argument on `cases.upsert_candidate` and
  `relevance.screen_range`, table `record_datasets` (migration 0005), dependencies
  `duckdb 1.5.6` and `pyarrow 25.0.1`.

### Crash-safe publication (A39)

1. The writer streams row groups into `staging/<artifact>/<attempt>/`.
2. On success it closes and `fsync`s both files, hashes them, and renames the attempt directory
   into `datasets/…` in one `os.replace`, then removes the empty staging folder.
3. The manifest row is committed in the same transaction that marks the artifact indexed.
4. Readers open only manifest paths, check the file size, and fail closed (HTTP 500 with no
   content) on a mismatch. `verify()` checks the SHA-256 digests.
5. A retry first deletes every unpublished directory of that artifact, then parses again.

Tested: a crash after the rename but before the commit leaves complete files that nothing reads,
and the retry removes them rather than adopting them. A killed writer leaves partial staging
files that are never read and are removed on retry. Exactly one dataset per artifact. Tampered
files are refused.

### Security (A40)

No client SQL reaches DuckDB. Each read is a fixed template with bound parameters, on a new
in-memory connection limited to the store directory, with external access, extension loading and
configuration changes locked. Tested: reading a file outside the store, enabling external access,
installing an extension and a manifest path that escapes the root are all refused. Permission
filtering happens in PostgreSQL on the manifest's access columns, which are copied from the
artifact, including an artifact classified more strictly than its source.

## 4. PostgreSQL vs Parquet/DuckDB, same 200,000 rows

`benchmarks/record_store_compare.py`: 200,000 synthetic rows (22.1 MB CSV), the real ingest code
and the same library read functions as the API, 30 timed calls per case after one warm-up, same
random query mix for both stores. Results: `results/record-store-compare-200k.json`.

| Measure | PostgreSQL index | Parquet + DuckDB |
| --- | ---: | ---: |
| Record storage on disk | 872.2 MB (39.5× source) | 37.2 MB (1.68× source): 34.6 MB records, 1.7 MB findings, manifest |
| Whole PostgreSQL database | 881.8 MB | 9.8 MB |
| Indexing time | 177.8 s (1,125 rows/s) | 39.0 s (5,135 rows/s), 4.6× faster |
| Peak resident memory while indexing (growth) | 140 MiB (+15) | 219 MiB (+81) |
| Answers identical (8 query types, 30 calls each) | | **All identical** |

Latency, p50 / p95 in ms:

| Query | PostgreSQL | Parquet + DuckDB |
| --- | ---: | ---: |
| Station lookup (indexed in PostgreSQL) | 2.8 / 3.4 | 18.6 / 19.7 |
| Narrow frequency window, page of 50 | 65.9 / 85.0 | 23.0 / 26.0 |
| Wide frequency window (150–450 MHz), page of 50 | 5.4 / 6.4 | 44.9 / 51.4 |
| Text search, page of 50 | 59.0 / 70.3 | 21.8 / 23.7 |
| Record detail (record, findings, station) | 3.2 / 3.8 | 33.0 / 38.5 |
| Preview, first page | 6.2 / 6.9 | 33.3 / 35.4 |
| Preview, deep page | 5.0 / 5.8 | 34.5 / 36.4 |
| Aggregation: count by record status | 58.2 / 60.6 | 10.4 / 10.9 |

Reading: Parquet wins on storage (23.5× smaller), indexing, scans and aggregation. PostgreSQL wins
on point lookups and early-terminating pages, which use its B-tree indexes; DuckDB has no index
and reads at least one 5,000-row row group per query. All Parquet latencies stay under 52 ms p95
at this size. The first Parquet run, before connections were reused and the duplicate record read
removed, was 141 ms for record detail and 391 MiB peak memory
(`results/record-store-compare-200k-before-connection-reuse.json`).

### Tuning tried after the first run

| Change | Effect (200,000 rows, one artifact) |
| --- | --- |
| One locked-down connection per thread instead of one per query | Saves ~21 ms per query; record detail 141 → 33 ms |
| Reuse the record read for the station fields | One fewer query per record detail |
| Row groups 20,000 → 5,000 rows | Peak indexing memory 391 → 219 MiB |
| Row groups 2,000 / 1,000 / 500 | No gain at 2,000; slower at 1,000 and 500 (point 33 / 53 ms, aggregation 30 / 55 ms), so 5,000 stays |
| Parquet metadata and object cache | Within noise for one file (`results/parquet-200k-metadata-cache.json`); ~17 % on 50 files |

### Many artifacts: the same 200,000 rows split over 50 artifacts

`results/record-store-compare-200k-50-artifacts.json`. Answers are not compared here, because the
order of cross-artifact results follows the per-database artifact IDs.

| Query, p50 / p95 ms | PostgreSQL | Parquet + DuckDB |
| --- | ---: | ---: |
| Station lookup | 8.8 / 9.8 | 162.8 / 165.7 |
| Narrow frequency window | 76.4 / 82.7 | 145.3 / 151.0 |
| Wide frequency window | 4.6 / 5.0 | 168.5 / 176.0 |
| Text search | 63.5 / 67.7 | 160.7 / 167.3 |
| Record detail | 5.2 / 5.9 | 25.5 / 27.6 |
| Preview page | 6.0 / 6.7 | 21.8 / 24.1 |
| Aggregation (one artifact) | 3.1 / 3.6 | 6.5 / 6.9 |
| Indexing | 238.0 s (840 rows/s) | 45.9 s (4,357 rows/s) |

Cross-artifact searches open every readable file: about 1.7 ms per file on this machine
(`count(*)` over 50 files takes 97 ms). That is linear in the number of readable artifacts: at
this rate 500 artifacts would take about 1.7 s, near the 2 s target (TR-NFR-006). The next step,
not built, is a per-source compaction: one consolidated, partitioned search file per source,
rebuilt when an artifact is published, so a search opens a few files instead of one per artifact.

## 6. Remaining limitations

- **Not enabled by default.** It needs joint review (A38) before it replaces the index.
- **No checkpoint resume.** A crash restarts the artifact's parse from the first row (also true of
  the PostgreSQL index). For tens of millions of rows this repeats work; chunked part files with
  per-chunk manifests would allow resume.
- **Migration** is by re-parse (`records_cli build`, A42), which needs the parser version the
  artifact was indexed with.
- **Cross-artifact search** opens one file per readable artifact (~1.7 ms each, measured at 50
  artifacts: ~160 ms). Per-source compaction is the planned fix; tens of millions of rows are
  unmeasured.
- **Ingest is parser-bound.** Python parsing and validation per record dominate after storage is
  removed from the path.
- **Recovery waits for the 5-minute lease**, measured in L1.
- **Review overrides of findings** have no storage yet; they must be a PostgreSQL overlay (A41).
- **Point lookups are slower** (20–45 ms instead of 3–6 ms at 200,000 rows) and grow with row-group
  size, not file size; untested at tens of millions of rows.
- **Indexing memory is higher** (+81 MiB at 5,000-row row groups) because rows are buffered before
  each row group is written.
- The PostgreSQL index's duplication (section 2) is left as it is, because the proposal moves those
  rows out rather than slimming them.

## 7. Exit criteria not yet verified

- 10 GiB upload and recovery (not run, as instructed).
- Indexing and querying 10 M / 50 M records end to end (only 200,000 rows were indexed in the
  comparison; 453,000 rows earlier on the PostgreSQL index).
- Queries over many artifacts at once, and concurrent query load.
- Recovery of a crash during parsing at scale (verified only in unit tests).
- Linux and production-like storage (object storage, network file systems): `os.replace`
  atomicity and `fsync` behaviour were tested on local NTFS only.
